# CBVA deployment (Vultr VPS + Caddy + Cloudflare, frontend on Cloudflare Pages)

```
Browser ──► app.<domain>  (Cloudflare Pages: Vite SPA)
   │
   └──────► api.<domain>  (Cloudflare proxy ─► Caddy :443 ─► api:8000 [FastAPI, 1 worker]) ─► external MongoDB
```

Replace the `example.com` placeholders in: `deploy/Caddyfile` (site address), `backend/.env` (`FRONTEND_ORIGIN=https://app.<domain>`),
and the Pages env var `VITE_API_URL=https://api.<domain>`. The CSP `connect-src` in `frontend/public/_headers` is rewritten
to the origin of `VITE_API_URL` at build time, so it needs no manual edit.

| File | Purpose |
|---|---|
| `docker-compose.yml`, `Caddyfile` | runtime stack (api + caddy); synced to `/opt/cbva` by CI |
| `cloudflare-ips.conf` | seed copy of Cloudflare ranges for Caddy `trusted_proxies`; the live copy on the VPS is regenerated by the cron script |
| `bootstrap-vps.sh`, `refresh-cloudflare-ips.sh` | one-time hardening; daily Cloudflare range sync (ufw **and** Caddy from one list) |
| `smoke-test.sh` | container checks (non-root, read-only, health, SIGTERM). Needs a Docker engine; CI runs it on every PR |
| `DATA_MIGRATION.md` | mongodump/mongorestore, index + count verification, "what an empty DB is missing" |

## 1. Cloudflare

1. DNS: `A api.<domain>` → the VPS **static** IPv4, **proxied (orange cloud)**.
2. SSL/TLS mode **Full (strict)**.
3. **Origin CA certificate** (SSL/TLS → Origin Server → Create certificate, hostname `api.<domain>`). Save the two files as
   `/opt/cbva/certs/origin.pem` and `/opt/cbva/certs/origin.key` (`chmod 600 origin.key`). Caddy serves them.
   *Why not Let's Encrypt:* the firewall (below) only admits Cloudflare on 80/443, so Let's Encrypt's validation servers
   cannot reach the origin and ACME issuance would fail.
4. Ingress is **Cloudflare-only on 80/443, and this is required, not optional.** The API takes the client IP from
   `CF-Connecting-IP` (set by Caddy from Cloudflare's header). That is only trustworthy if nothing but Cloudflare can reach
   Caddy. `bootstrap-vps.sh` does this by default (ufw `allow from <each Cloudflare range> to any port 80,443`), and a cron
   (`/etc/cron.d/cbva-cloudflare-ips`, daily 03:17) re-fetches https://www.cloudflare.com/ips-v4 and `/ips-v6`, updates ufw
   and `/opt/cbva/cloudflare-ips.conf`, and reloads Caddy. SSH (22) stays open, restricted to `SSH_ALLOW_IP` if you set it.
   Verify: `ufw status | grep cloudflare-web | wc -l` (22 at time of writing) and `ufw status | grep -E '^(80|443)/tcp +ALLOW +Anywhere'` (must print nothing).

Defence in depth (all tested, see `backend/tests/test_rate_limit_proxy.py`): even with the firewall, the app honours
`CF-Connecting-IP` only from a private-network peer (`TRUSTED_PROXY_CIDRS`, i.e. the Caddy container), Caddy overwrites the
header with the Cloudflare-verified IP, and uvicorn runs `--no-proxy-headers` so the peer address is never rewritten.

## 2. Cloudflare Pages (frontend)

| Setting | Value |
|---|---|
| Root directory | `frontend` |
| Build command | `npm ci && npm run build` |
| Build output directory | `dist` |
| `NODE_VERSION` (env var) | `22` (any current LTS; local dev used 24) |
| `VITE_API_URL` (env var, **Production and Preview**) | `https://api.<domain>`: the build **fails** if it is missing or contains localhost/127.0.0.1 |
| Custom domain | `app.<domain>` |

> **Warning: preview deployments (`*.pages.dev`) are NOT allowed by the backend CORS.** `FRONTEND_ORIGIN` lists exact origins
> and `CORS_ORIGIN_REGEX` is empty. A preview build loads but every API call is blocked. Disable previews, or temporarily
> add one specific preview origin to `FRONTEND_ORIGIN`.

`public/_headers` (CSP etc.) and `public/_redirects` (SPA fallback) end up in `dist/` and are honoured by Pages. `frontend/vercel.json`
is untouched and unused on Pages. CSP is `script-src 'self'` (no inline/eval), `img-src 'self' data:`, fonts from Google Fonts only.
Add any new third-party origin to `_headers` and re-run `node scripts/verify-csp.mjs` after a build.

## 3. MongoDB (Atlas or self-managed) allowlist checklist

- [ ] Reserve a **static IPv4** on Vultr so the allowlist survives a rebuild.
- [ ] Atlas Network Access: only `<vps-ip>/32`. Remove `0.0.0.0/0`.
- [ ] Dedicated DB user with `readWrite` on the app database only.
- [ ] Region near the VPS (Mumbai `ap-south-1`). The app opens ≤ 10 connections (M0 caps at 500 / 512 MB).
- [ ] Backups on; do one test restore into a scratch database.
- [ ] Rotate any credential that ever lived in a developer's `.env` (`MONGODB_URL_PROD_READ`).
- [ ] Alerts on connections, disk, replication lag.

## 4. VPS setup

```bash
# from your laptop; both files must sit together
scp deploy/bootstrap-vps.sh deploy/refresh-cloudflare-ips.sh root@<vps-ip>:/root/
ssh root@<vps-ip> 'SSH_ALLOW_IP=<your.ip> bash bootstrap-vps.sh deploy "<paste PUBLIC key text>"'   # omit SSH_ALLOW_IP to leave 22 open to all
# open a SECOND terminal and confirm: ssh deploy@<vps-ip>  (before closing the first)
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256   # run on the VPS: value for SSH_HOST_FINGERPRINT
```

As `deploy` in `/opt/cbva` place: `docker-compose.yml`, `Caddyfile` (CI also syncs these two), `certs/origin.pem|key`, and `.env`
(`chmod 600`, from `backend/.env.example`, `ENV=prod`, `SECRET_KEY` = `openssl rand -hex 32`). `cloudflare-ips.conf` is created
by the bootstrap script.

GitHub **environment** `production` (add reviewers if you want manual approval) with secrets:

| Secret | Value |
|---|---|
| `SSH_HOST`, `SSH_USER` | VPS address, `deploy` |
| `SSH_KEY` | private key for `deploy` |
| `SSH_HOST_FINGERPRINT` | `SHA256:...` from the command above: pins the host key (no `StrictHostKeyChecking=no`) |
| `GHCR_PULL_USER`, `GHCR_PULL_TOKEN` | GitHub user + PAT with `read:packages` that the VPS uses to pull |

## 5. First-run order

```bash
cd /opt/cbva
export GHCR_OWNER=<github-owner> TAG=<image-tag>      # CI records the tag in .current_tag
docker login ghcr.io -u <user>                          # PAT with read:packages
docker compose pull

# (migrating existing data? do deploy/DATA_MIGRATION.md steps 1-2 now, before bootstrap)

# 1) Bootstrap: first admin + KRA seed + current FY (idempotent). Needs ADMIN_EMAIL / ADMIN_PASSWORD (>= 12 chars) in .env
docker compose run --rm --no-deps api python -m app.cli bootstrap

# 2) Look for leftover demo accounts (admin@cbva.com, mm@*, vc@*): read-only, exit 1 if any are found
docker compose run --rm --no-deps api python -m app.cli check-demo-users
docker compose run --rm --no-deps api python -m app.cli check-demo-users --deactivate   # once your real admin works

# 3) Start and verify
docker compose up -d
docker compose ps                                       # api -> healthy
curl -fsS https://api.<domain>/health/ready             # {"status":"ok","db":"up",...}
docker compose run --rm --no-deps api python -m app.cli verify-indexes
docker stats --no-stream                                # api RSS well under 700 MiB
```

Remove `ADMIN_EMAIL` / `ADMIN_PASSWORD` from `.env` after step 1. Bootstrap does **not** create leaders (it needs real
names/practices) and warns if `leaders` is empty. `GET /api/consolidated-summary` returns **503** until a
`consolidated_summaries` document exists for the FY. See `DATA_MIGRATION.md` §5 for the full screen-to-data checklist.

## 6. Rollback

1. The deploy job records `/opt/cbva/.current_tag` and `.previous_tag`. If pull, start or the health check fails it
   **automatically** re-deploys the previous tag (an ERR trap, simulated against a stub docker for four scenarios).
2. Manual: `cd /opt/cbva && export GHCR_OWNER=<owner> TAG=$(cat .previous_tag) && docker compose up -d api && curl -fsS https://api.<domain>/health/ready && echo $TAG > .current_tag`.
3. No schema migrations in code (index creation is additive), so no DB rollback step. For data problems restore the Atlas
   snapshot into a **new** database and switch `DATABASE_NAME`.
4. Frontend: Pages → Deployments → roll back to the previous build.
5. Keep the last 3 image tags in GHCR.

## 7. Operating notes

- One uvicorn worker, `mem_limit: 700m`, 2 GB swap. Do not raise workers on 1 vCPU / 1 GB.
- Login limiter (5/min per client IP) and per-email throttle (10 per 15 min, in-process) reset on container restart; fine for one
  instance. Note the per-email throttle also lets someone lock a known email out for 15 minutes; accepted trade-off.
- `/health` is liveness (no DB); `/health/ready` pings Mongo (2 s timeout, 503 if down) and is used by Docker, Caddy and CI.
- `ENV=prod` disables `/docs`, `/redoc`, `/openapi.json`.
- Tokens live in browser `localStorage` (access 15 min, refresh 7 days, rotated with a unique `jti`, revoked on password change /
  deactivation / logout). The CSP is the main XSS mitigation.
- Reads can write: `GET /api/appraisals/*`, collections, blue-sky and EL summary create rows on first read, and `GET /api/consolidated-summary` can import.
